## Standing constraints

These are the ones a cold agent gets wrong. The full set is in `CLAUDE.md`.

- **Never push to `master`.** Work on a branch named for the work, open a pull
  request. A merge is a production release.
- **A production write needs the owner's approval immediately before it** - not
  earlier in the session, not implied by a plan, never carried over from the
  previous write. Reads are fine.
- **Test before code**, and state in the test what it would fail to detect.
- **Prove claims.** Re-measure the passing test count rather than quoting one
  from a document; a handoff in this repository once recorded 982 when the real
  figure was 1,036.
- **English everywhere**: code, comments, test names, commits, pull requests.
- **A change that alters what the system does, refuses or costs lands its
  decision in `DECISIONS.md` in the same pull request, with its condition.**
- Before claiming anything is done, run and paste real output:
  `ruff check .`, `ruff format --check .`, `pytest`,
  `zizmor --no-online-audits .github/workflows/`.

## One open review note on pull request #27

The workflow shares the `e2026-live-fetcher` concurrency group, which is right
for Supabase contention and has a consequence nobody has written down:
`cancel-in-progress: false` keeps at most one *pending* run per group, so a
dispatched verification can be cancelled by the next scheduled chain run, and a
cancelled dispatch produces no result and no error. Dispatch it while the chain
is idle. If that turns out to bite, the fix is a separate concurrency group plus
an explicit wait, not `cancel-in-progress: true`.
